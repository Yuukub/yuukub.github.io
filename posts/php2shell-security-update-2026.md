ช่วงนี้ใครตามข่าวความปลอดภัยเว็บไซต์น่าจะเห็นชื่อ **PHP2Shell** ผ่านตากันบ้างครับ หลายคนรู้ว่าต้องอัปเดต แต่พอเข้า WordPress แล้วเห็นว่า Core กับปลั๊กอินเป็นรุ่นล่าสุด ก็อาจคิดว่าจัดการครบแล้ว

รอบนี้ต้องตรวจต่ออีกชั้นครับ เพราะปัญหาอยู่ใน **PHP ที่เซิร์ฟเวอร์ใช้รันเว็บไซต์** การกดอัปเดตในหลังบ้าน WordPress ไม่ได้อัปเดต PHP ของโฮสติ้งให้ด้วย

ผมเขียนบทความนี้สำหรับเจ้าของเว็บและคนที่ต้องดูแลหลายเว็บไซต์ อยากให้เช็กกันได้ว่าเว็บของเราใช้ PHP รุ่นไหน ได้รับแพตช์แล้วหรือยัง และต้องถามอะไรจากผู้ให้บริการ โดยอ้างอิงข้อมูลที่ตรวจสอบถึงวันที่ **29 ตุลาคม 2026**

## PHP2Shell คืออะไร ทำไมถึงมีคนพูดถึงกันมาก

PHP2Shell เป็นชื่อที่ใช้เรียกช่องโหว่ **CVE-2026-109618** และ **CVE-2026-109619** ทั้งคู่มีคะแนนความรุนแรง **CVSS v4.0 เท่ากับ 9.2** และอาจเปิดให้ผู้โจมตีที่ไม่ต้องล็อกอินสั่งรันโค้ดบนเซิร์ฟเวอร์ได้เมื่อเข้าเงื่อนไข ตาม [คำเตือนของ NHS England](https://digital.nhs.uk/cyber-alerts/2026/cc-4875)

คำว่า Remote Code Execution หรือ RCE หมายถึงการที่ผู้โจมตีทำให้ระบบรันโค้ดที่ตนควบคุมได้ หากเกิดขึ้นจริง ความเสียหายจะขึ้นกับสิทธิ์ของโปรเซส PHP และการแยกสิทธิ์บนเซิร์ฟเวอร์ เช่น อาจอ่านไฟล์ที่โปรเซสเข้าถึงได้ แก้เนื้อหาเว็บ หรือวางไฟล์อันตรายเพิ่ม

ที่ต้องรีบจัดการคือเรื่องนี้มีความคืบหน้าแล้วครับ [Canadian Centre for Cyber Security อัปเดตคำเตือนเมื่อวันที่ 27 ตุลาคม](https://www.cyber.gc.ca/en/alerts-advisories/al26-026-critical-vulnerabilities-impacting-php-cve-2026-109618-cve-2026-109619) ว่ามีรายงานการโจมตีจริง และ CISA เพิ่มช่องโหว่ทั้งสองเข้า Known Exploited Vulnerabilities เมื่อวันที่ 26 ตุลาคม อย่างไรก็ตาม ข้อมูลนี้ไม่ได้แปลว่าทุกเว็บที่ใช้ PHP ถูกเจาะไปแล้ว ต้องตรวจรุ่น แพตช์ และหลักฐานของแต่ละระบบประกอบกัน

## ช่องโหว่สองตัวนี้ทำงานผิดพลาดตรงไหน

ทั้งสองปัญหาเกี่ยวข้องกับการจัดการหน่วยความจำและสถานะภายใน PHP ผมอธิบายคร่าว ๆ เพื่อให้เห็นว่าทำไมการตรวจแค่โค้ดของเว็บไซต์จึงไม่พอครับ

| ช่องโหว่ | ปัญหาที่เกิดขึ้น |
| --- | --- |
| [CVE-2026-109618](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w) | ระหว่างเกิดภาวะหน่วยความจำไม่พอ ข้อมูลภายในบางส่วนอาจยังเตรียมไม่เสร็จ แต่ขั้นตอนเก็บกวาดคำขอกลับนำข้อมูลนั้นไปใช้ จนเกิดความเสียหายในหน่วยความจำและอาจนำไปสู่ RCE |
| [CVE-2026-109619](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp) | สถานะภายในบางส่วนอาจยังอ้างถึงหน่วยความจำของคำขอก่อนหน้าที่ถูกคืนไปแล้ว เมื่อ worker เดิมรับคำขอถัดมา จึงอาจนำสถานะที่ค้างนั้นกลับมาใช้ |

ตาม [คำอธิบายจาก PHP Foundation](https://thephp.foundation/blog/2026/10/21/todays-php-security-release-and-how-were-strengthening-php-security/) มีการสาธิต RCE บน Apache ที่ใช้ mod_php และยืนยันเส้นทางโจมตีผ่านโค้ดแอปพลิเคชันบน PHP-FPM สำหรับปัญหา OOM ด้วย จึงไม่ควรสรุปว่าใช้ Nginx หรือ PHP-FPM แล้วข้ามข่าวนี้ได้

PHP ระบุให้ตรวจระบบที่รับ web request ทั้ง PHP-FPM, mod_php, php-cgi, FrankenPHP และ LiteSpeed โดยประเมินความเสี่ยงสูงสุดไว้ที่ mod_php ดูรายละเอียดใน [ประกาศความปลอดภัยวันที่ 21 ตุลาคม](https://www.php.net/archive/2026.php#2026-10-21-5)

## ต้องอัปเดต PHP เป็นรุ่นไหน

แพตช์สำหรับ **สองช่องโหว่ PHP2Shell** ออกเมื่อวันที่ **21 ตุลาคม 2026** รุ่นที่เริ่มมีตัวแก้ในแต่ละสายมีดังนี้ ตาม [ตารางรุ่นแก้ไขจาก NHS England](https://digital.nhs.uk/cyber-alerts/2026/cc-4875) และ [advisory ของ PHP](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w)

| สาย PHP | รุ่นก่อนแพตช์ในสายนั้น | รุ่นที่เริ่มแก้ PHP2Shell |
| --- | --- | --- |
| 8.2 | ก่อน 8.2.35 | **8.2.35** |
| 8.3 | ก่อน 8.3.36 | **8.3.36** |
| 8.4 | ก่อน 8.4.27 | **8.4.27** |
| 8.5 | ก่อน 8.5.12 | **8.5.12** |

ตารางนี้ใช้ตอบว่ารุ่นใดเริ่มมีแพตช์ของสองช่องโหว่นี้ครับ หากอ่านภายหลัง ให้ตรวจรุ่นเสถียรล่าสุดของสายที่ใช้งานและประกาศจากผู้ให้บริการอีกครั้ง ไม่จำเป็นต้องหยุดอัปเดตไว้ที่ตัวเลขในตาราง

สำหรับแพ็กเกจจาก Linux distribution หรือผู้ให้บริการ LTS อาจมีการนำแพตช์กลับมาใส่ในแพ็กเกจรุ่นเดิม หรือที่เรียกว่า **backport** ดังนั้นอย่าใช้เลขเวอร์ชัน PHP เพียงอย่างเดียวตัดสินว่าได้รับแพตช์แล้วหรือยัง ให้ตรวจประกาศ แพ็กเกจ revision และ CVE ที่ผู้จำหน่ายยืนยันว่าแก้แล้วด้วย

หากยังใช้ PHP 7.4, 8.0 หรือ 8.1 ต้องคุยกับผู้ให้บริการให้ชัดเจนครับ สายเหล่านี้อยู่ใน [รายการที่หมดการสนับสนุนจาก PHP](https://www.php.net/eol.php) แล้ว แม้รอบนี้จะมี source-backport แบบจำกัดให้ ก็ไม่ได้ทำให้กลับมาได้รับการดูแลตามปกติ ควรเร่งตรวจแพตช์ที่ใช้อยู่และวางแผนย้ายไป [สายที่ยังรองรับ](https://www.php.net/supported-versions.php)

## ใช้ WordPress แล้วควรเริ่มตรวจตรงไหน

อย่างแรก ลองเข้า **เครื่องมือ → สุขภาพเว็บไซต์ → ข้อมูล → เซิร์ฟเวอร์** เพื่อดู PHP ที่เว็บกำลังใช้อยู่ แล้วเทียบกับข้อมูลในแผงโฮสติ้ง หากบัญชีเดียวมีหลายโดเมน ให้ตรวจแยกทีละเว็บ เพราะแต่ละโดเมนอาจตั้งค่า PHP คนละรุ่น

ถ้ามีสิทธิ์เข้าเซิร์ฟเวอร์ คำสั่ง `php -v` ช่วยดูรุ่นของ PHP ฝั่ง command line ได้ แต่ต้องตรวจ PHP ที่รับคำขอเว็บจริงด้วย เพราะ CLI กับ PHP-FPM หรือ Apache อาจใช้คนละรุ่นและคนละ configuration

สิ่งที่ผมแนะนำให้ตรวจมีดังนี้ครับ

1. **ทำรายการเว็บและ PHP ที่ใช้งานจริง** รวมเว็บเก่า เว็บทดสอบ subdomain และ container ที่ยังเปิดรับจากอินเทอร์เน็ต
2. **ยืนยันแพตช์กับโฮสติ้ง** ขอข้อมูลว่าระบบของเราแก้ CVE ทั้งสองแล้วหรือยัง ไม่หยุดแค่คำตอบว่าใช้ PHP 8 อยู่
3. **สำรองและทดสอบก่อนเปลี่ยนรุ่น** โดยเฉพาะเว็บที่ต้องย้ายจาก PHP เก่าข้ามสายหลัก ให้ลองธีม ปลั๊กอิน และโค้ดเฉพาะของเว็บบน staging ก่อน
4. **ให้ผู้ดูแลนำแพตช์ขึ้นใช้งานจริง** รวมการ restart หรือ reload บริการตามคู่มือของแพ็กเกจ แล้วตรวจว่า worker ที่ให้บริการอยู่ใช้ตัวแก้แล้ว
5. **ทดสอบงานสำคัญหลังอัปเดต** ทั้งล็อกอิน ฟอร์ม อัปโหลดไฟล์ ระบบสมาชิก และเช็กเอาต์ พร้อมดู error log ประกอบ

ถ้าไม่มีทีมดูแลเซิร์ฟเวอร์ สามารถส่งข้อความนี้ให้โฮสติ้งได้เลยครับ

> ขอให้ช่วยตรวจ PHP ที่ให้บริการเว็บไซต์ทุกโดเมนในบัญชี ว่าได้รับแพตช์ CVE-2026-109618 และ CVE-2026-109619 แล้วหรือยัง หากใช้ backport ขอเลขแพ็กเกจและประกาศยืนยัน พร้อมตรวจว่าบริการหรือ worker ได้โหลดแพตช์ใหม่แล้ว และมีคำแนะนำเพิ่มเติมสำหรับ CVE-2026-115560 หรือไม่

การอัปเดต Core ปลั๊กอิน และธีมยังต้องทำต่อไป แต่ต้องตรวจ PHP แยกด้วยครับ ใครอยากย้อนอ่านเรื่องการตามแพตช์ WordPress ดูได้ที่ [WordPress 7.1.3 และเหตุผลที่ช่วงนี้อัปเดตบ่อย](/th/blog/wordpress-7-1-3-security-update/)

## แล้วข่าวช่องโหว่ที่ประกาศตามมาวันที่ 23 ตุลาคมล่ะ

หลังแพตช์ PHP2Shell มีประกาศเรื่อง **Session upload progress** ตามมาอีกตัว คือ **CVE-2026-115560** ซึ่งแพตช์วันที่ 21 ตุลาคมยังไม่ครอบคลุม ตาม [คำเตือนที่อัปเดตจาก Cyber Centre](https://www.cyber.gc.ca/en/alerts-advisories/al26-026-critical-vulnerabilities-impacting-php-cve-2026-109618-cve-2026-109619)

เงื่อนไขของตัวนี้เฉพาะกว่าครับ ต้องมีการตั้ง `session.serialize_handler` เป็น `php_binary` หรือ `php_serialize` แล้วโค้ดเปลี่ยนกลับเป็น `php` ด้วย `ini_set()` ก่อนเรียก `session_start()` ขณะที่ยังเปิด Session upload progress อยู่ แอปพลิเคชันที่ไม่เปลี่ยน serialize handler ระหว่างทำงานไม่เข้าเส้นทางโจมตีนี้ ตาม [ประกาศ PHP วันที่ 23 ตุลาคม](https://www.php.net/archive/2026.php)

ณ วันที่ตรวจสอบ PHP แนะนำให้ปิดฟีเจอร์นี้ระหว่างรอรอบแก้ไขตามปกติ โดยให้ผู้ดูแลประเมินการใช้งานก่อน

```ini
session.upload_progress.enabled=0
```

การตั้งค่านี้ควรทำใน `php.ini` หรือ configuration ระดับบริการที่มีผลก่อน PHP เริ่มอ่านคำขอ และ restart worker ให้ครบ ไม่อาศัย `ini_set()` ในโค้ดเว็บหรือ `.user.ini` ของ FPM เพียงอย่างเดียว ดู [คำแนะนำด้าน Session upload progress ใน advisory](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp)

อย่างไรก็ตาม การปิดฟีเจอร์นี้ไม่แทนการลงแพตช์ PHP2Shell สองตัวแรก และไม่ควรเปลี่ยนค่าเซิร์ฟเวอร์ตามคำแนะนำที่ตัดมาสั้น ๆ โดยไม่อ่านเงื่อนไขครับ

**สำหรับ Windows** มีประกาศวันที่ 26 ตุลาคมให้ใช้แพ็กเกจ rebuild ที่ลงท้าย `-1` ซึ่งอัปเดต Brotli แก้ CVE-2026-111497 เพิ่มเติมด้วย ประเด็นนี้เกี่ยวข้องกับการเปิดถอดรหัส HTTP response อัตโนมัติผ่าน cURL ซึ่งไม่ได้เปิดเป็นค่าเริ่มต้น ตัวเลข PHP runtime ยังเหมือนเดิม จึงต้องตรวจรุ่นแพ็กเกจประกอบ ดู [ประกาศ Windows builds จาก PHP](https://www.php.net/archive/2026.php)

## ยังอัปเดตไม่ได้วันนี้ ควรทำอย่างไร

ให้ติดต่อโฮสติ้งหรือผู้ดูแลเพื่อกำหนดเวลาลงแพตช์ทันทีครับ หากระบบยังเปิดรับจากอินเทอร์เน็ตและยังแก้ไม่ได้ ควรประเมินการจำกัดการเข้าถึงหรือแยกระบบชั่วคราวกับผู้ดูแล ตาม [แนวทางของ Cyber Centre](https://www.cyber.gc.ca/en/alerts-advisories/al26-026-critical-vulnerabilities-impacting-php-cve-2026-109618-cve-2026-109619)

WAF อาจช่วยกรองการโจมตีบางรูปแบบได้ แต่ไม่ได้ยืนยันว่าครอบคลุมทุกเส้นทาง PHP ระบุว่าการอัปเดตเป็นวิธีแก้ที่ครบถ้วน ส่วนการปรับ configuration เป็นการลดความเสี่ยงเฉพาะบางเส้นทางเท่านั้น ดู [ข้อจำกัดของมาตรการชั่วคราวจาก PHP](https://www.php.net/archive/2026.php#2026-10-21-5)

สำหรับคนที่มีหลายเว็บ ผมอยากให้เริ่มจากรายการที่ตรวจตามได้ว่าแต่ละเว็บอยู่บนเซิร์ฟเวอร์ไหน ใช้ PHP อะไร ใครเป็นคนลงแพตช์ และตรวจผลเมื่อไร วิธีนี้ช่วยให้ตามเว็บที่ตกหล่นได้ดีกว่าจำว่าอัปเดตเครื่องหลักไปแล้ว

## ลงแพตช์แล้ว อย่าลืมตรวจสิ่งที่เกิดขึ้นก่อนหน้า

การอัปเดตปิดช่องโหว่ แต่ไม่ได้ลบไฟล์อันตรายหรือบัญชีที่อาจถูกสร้างไว้ก่อนหน้า หากพบไฟล์ PHP แปลกปลอม ผู้ดูแลที่ไม่รู้จัก process หรือการเชื่อมต่อออกที่ผิดปกติ ควรเก็บหลักฐานและตรวจเหตุการณ์เพิ่มเติม แนวทางตรวจ log และความผิดปกติเหล่านี้อยู่ใน [คำแนะนำของ Cyber Centre](https://www.cyber.gc.ca/en/alerts-advisories/al26-026-critical-vulnerabilities-impacting-php-cve-2026-109618-cve-2026-109619)

สิ่งที่อยากให้ทำหลังอ่านคือเปิดดู PHP ของเว็บตัวเอง แล้วขอคำยืนยันเรื่องแพตช์จากคนที่ดูแลเครื่องครับ โดยเฉพาะเว็บที่อัปเดต WordPress สม่ำเสมอแต่ไม่ได้ตรวจ PHP มานาน รอบนี้ควรตรวจให้ครบทั้งสองส่วน

*ตรวจสอบข้อมูล ณ วันที่ 29 ตุลาคม 2026 ตารางรุ่นในบทความระบุแพตช์เริ่มต้นของ PHP2Shell สอง CVE เท่านั้น ก่อนดำเนินการให้ตรวจประกาศ PHP และผู้จำหน่ายแพ็กเกจล่าสุดอีกครั้ง*
