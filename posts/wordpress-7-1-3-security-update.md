ช่วงนี้ใครดูแลเว็บ WordPress น่าจะสังเกตว่าอัปเดตกันบ่อยครับ เพิ่งลงรุ่นใหม่ไปไม่นานก็มีแจ้งเตือนมาอีกแล้ว บางคนอาจเริ่มสงสัยว่ามีอะไรเกิดขึ้น หรือจะรออัปเดตทีเดียวตอนที่ไม่มีแพตช์ตามมาอีกดี

รอบนี้ผมอยากชวนให้รีบอัปเดตครับ เพราะเป็นการแก้ความปลอดภัย และการที่เว็บยังเปิดได้ตามปกติก็ไม่ได้บอกว่าช่องโหว่ถูกปิดแล้ว ผมมีเคสลูกค้าที่ต้องเข้าไปแก้มัลแวร์ทั้งเซิร์ฟเวอร์เกือบ 100 เว็บ ซึ่งเป็นตัวอย่างว่าการปล่อย Core เก่าไว้ทำให้งานดูแลเว็บหนักขึ้นแค่ไหน

**WordPress Core 7.1.3 ออกเมื่อวันที่ 6 ตุลาคม 2026** เป็นรุ่น Maintenance and Security ที่แก้ความปลอดภัย 7 จุดและบั๊กอีก 4 จุด ทีม WordPress แนะนำให้อัปเดตทันที ตาม [ประกาศ WordPress 7.1.3](https://wordpress.org/news/2026/10/wordpress-7-1-3-maintenance-and-security-release/)

> [!IMPORTANT]
> หากดูแลเว็บ WordPress ให้ตรวจเวอร์ชันและเริ่มสำรองข้อมูลเพื่ออัปเดตโดยเร็ว หากอ่านบทความนี้ภายหลังวันที่ 7 ตุลาคม 2026 ให้ตรวจ [รุ่นล่าสุดจาก WordPress.org](https://wordpress.org/download/) อีกครั้ง เพราะอาจมีแพตช์ใหม่กว่า 7.1.3 แล้ว

## ทำไมช่วงนี้ WordPress อัปเดตบ่อย

ลองดูสามรุ่นล่าสุดครับ ออกห่างกันไม่นาน และทุกรอบมีเรื่องความปลอดภัยที่ต้องแก้

| รุ่น | วันที่ออก | สิ่งที่ผู้ดูแลเว็บควรรู้ |
| --- | --- | --- |
| [7.1.1](https://wordpress.org/news/2026/09/wordpress-7-1-1-maintenance-and-security-release/) | 17 กันยายน 2026 | แก้ความปลอดภัย 11 จุด พร้อมบั๊กใน Core และ Block Editor |
| [7.1.2](https://wordpress.org/news/2026/09/wordpress-7-1-2-release/) | 22 กันยายน 2026 | แก้ช่องโหว่ระดับ Critical ที่อาจนำไปสู่การรันโค้ดจากระยะไกลเมื่อเข้าเงื่อนไข |
| [7.1.3](https://wordpress.org/news/2026/10/wordpress-7-1-3-maintenance-and-security-release/) | 6 ตุลาคม 2026 | แก้ความปลอดภัยเพิ่มอีก 7 จุด และบั๊ก 4 จุด |

ทีม WordPress อธิบายเรื่องนี้ไว้ในประกาศ [Core Security Initiative](https://make.wordpress.org/security/2026/08/28/the-core-security-initiative/) ว่ามีรายงานปัญหาความปลอดภัยเข้ามามากขึ้น ส่วนหนึ่งเพราะ AI ช่วยให้นักวิจัยตรวจโค้ดและหาจุดผิดพลาดได้มากขึ้น ทีมจึงต้องเพิ่มคนมาคัดกรองและแก้รายงานที่ค้างอยู่ รวมถึงปรับขั้นตอนออกแพตช์และใช้ AI ช่วยตรวจหาช่องโหว่ด้วย

สำหรับคนดูแลเว็บ ผมมองว่าเราควรตามแพตช์ให้ทันครับ เมื่อมีคนพบปัญหาและออกตัวแก้มาแล้ว การรอให้การอัปเดต “นิ่ง” อาจทำให้เรายังใช้รุ่นที่มีช่องโหว่ต่อไปอีกหลายสัปดาห์ ส่วนจะถูกโจมตีไปแล้วหรือไม่ ต้องตรวจเว็บจริง จำนวนแพตช์ที่ออกบอกเรื่องนี้ไม่ได้

## 7.1.3 แก้อะไรบ้าง

ใน [ประกาศรุ่น 7.1.3](https://wordpress.org/news/2026/10/wordpress-7-1-3-maintenance-and-security-release/) มีการแก้ความปลอดภัย 7 จุด ผมสรุปไว้ในตารางนี้ครับ

| ประเด็นที่แก้ | ความหมายสำหรับผู้ดูแลเว็บ |
| --- | --- |
| Stored XSS ในหน้าจัดการความคิดเห็น ผ่านคอมเมนต์ที่รออนุมัติ | ข้อมูลคอมเมนต์อาจพาสคริปต์อันตรายเข้าไปทำงานในเบราว์เซอร์ของผู้ดูแล |
| DoS ใน `WP_Http::make_absolute_url()` | การประมวลผล URL มีจุดที่อาจกระทบความพร้อมใช้งานของระบบ |
| Second-order SQL Injection ในการส่งออก WXR | ข้อมูลที่จัดเก็บไว้อาจส่งผลต่อคำสั่งฐานข้อมูลตอนส่งออกเนื้อหา |
| ผู้ใช้บทบาท Author ปักหมุดโพสต์ได้ | การตรวจสิทธิ์เปิดให้ทำบางอย่างเกินขอบเขตของบทบาท |
| เปิดเผยความคิดเห็นของโพสต์ส่วนตัวหรือยังไม่เผยแพร่โดยไม่ต้องล็อกอิน | เนื้อหาที่ควรจำกัดการเข้าถึงอาจหลุดออกไป |
| XSS จาก Imgur embeds | เนื้อหาฝังจากภายนอกมีประเด็นเกี่ยวกับการรันสคริปต์ |
| พารามิเตอร์ของ hook `{status}_{type}` ปลอมแปลงได้จนชื่อ action ชนกัน | กลไกเรียกงานตามสถานะและชนิดโพสต์อาจถูกชักนำให้ผิดจากที่คาด |

ไม่ใช่ทุกข้อจะโจมตีได้ด้วยวิธีเดียวกัน บางข้อเกี่ยวข้องกับบัญชีผู้ใช้ บางข้อกับข้อมูลหรือฟีเจอร์เฉพาะ และประกาศนี้ไม่ได้ระบุว่าทั้ง 7 ข้อเป็นระดับ Critical หรือทำให้ยึดเซิร์ฟเวอร์ได้ทั้งหมด

ถ้าไม่คุ้นกับชื่อช่องโหว่ ลองอ่านคำอธิบายสั้น ๆ นี้ครับ

- **XSS:** สคริปต์อันตรายทำงานในเบราว์เซอร์ภายใต้บริบทของเว็บ ผลจริงขึ้นกับหน้าที่เกิดปัญหา สิทธิ์ผู้ใช้ และมาตรการป้องกันอื่น
- **SQL Injection:** ข้อมูลแทรกแซงคำสั่งฐานข้อมูลได้ ส่วนคำว่า *second-order* หมายถึงปัญหาที่ไปเกิดตอนนำข้อมูลที่เก็บไว้กลับมาใช้ภายหลัง
- **DoS:** ทำให้บริการช้าหรือใช้งานไม่ได้ ไม่ได้หมายความว่าโจรกรรมข้อมูลสำเร็จเสมอไป
- **Information Disclosure:** ข้อมูลที่ควรเป็นส่วนตัวถูกเปิดเผย แม้หน้าเว็บยังดูปกติ
- **Authorization flaw:** ระบบตรวจสิทธิ์ไม่ครบ ทำให้ผู้ใช้ทำสิ่งที่บทบาทของตนไม่ควรทำได้

## ใครยังไม่ได้ลง 7.1.2 ยิ่งไม่ควรรอ

รุ่น [7.1.2](https://wordpress.org/news/2026/09/wordpress-7-1-2-release/) แก้ช่องโหว่ระดับ **Critical** ซึ่งผู้โจมตีที่ไม่ต้องล็อกอินอาจทำให้ระบบเลือกโหลดไฟล์ PHP ภายในเครื่องที่อ่านได้จากนอกไดเรกทอรีธีมที่ใช้งานอยู่ และอาจนำไปสู่ **Remote Code Execution (RCE)** เมื่อสภาพแวดล้อมเซิร์ฟเวอร์และธีมเข้าเงื่อนไข

RCE หมายถึงผู้โจมตีสั่งให้ระบบรันโค้ดได้ ความเสียหายที่อาจตามมาขึ้นกับสิทธิ์ของโปรเซส เช่น เปลี่ยนเนื้อหา ฝังไฟล์อันตราย หรือเข้าถึงข้อมูลที่ระบบนั้นอ่านได้ อย่างไรก็ตาม ไม่ควรเหมารวมว่าทุกเว็บที่ยังไม่อัปเดตถูกยึดแล้ว

หากยังใช้ 7.1 หรือ 7.1.1 **อย่าหยุดที่ 7.1.2 ให้ไปยังรุ่นเสถียรล่าสุดที่ตรวจสอบแล้ว** เพราะ 7.1.3 มีการแก้เพิ่มเติม ส่วนเว็บที่อัปเดต 7.1.2 แล้วก็ยังต้องลงแพตช์รอบใหม่นี้

## เคสลูกค้าในญี่ปุ่นที่ให้ผมแก้มัลแวร์ทั้งเซิร์ฟเวอร์เกือบ 100 เว็บ

เคสหนึ่งที่ผมเข้าไปแก้เป็นลูกค้าคนไทยที่ทำบริษัทอยู่ในญี่ปุ่นครับ เขามีเว็บไซต์จำนวนมาก และงานที่ให้ผมเข้าไปจัดการครอบคลุมทั้งเซิร์ฟเวอร์ รวมแล้วเกือบ 100 เว็บ

ก่อนติดต่อมา ทีมของลูกค้าพยายามแก้กันเองแล้ว รวมถึงเอา AI เข้ามาช่วย แต่พอมีเว็บเยอะขนาดนี้ ค่าโทเคนก็สูงตามไปด้วย และการแก้แต่ละเว็บยังใช้เวลามาก ทีมจึงดูแลต่อเองไม่ไหว สุดท้ายเลยมาใช้บริการของผมเพื่อเข้าไปจัดการให้

ต้นทางของเคสนี้คือช่องโหว่ร้ายแรงใน WordPress Core ที่ไม่ได้อัปเดต และระบบยังใช้ PHP 7.4 อยู่ด้วยครับ เรื่องนี้ทำให้เห็นว่าการมีทีมดูแลหรือมี AI ช่วย ไม่ได้ลดภาระลงเสมอไป หากต้องตามแก้ปัญหาทีละเว็บหลังถูกโจมตีแล้ว ยิ่งมีเว็บไซต์มาก ค่าใช้จ่ายและเวลาที่ต้องใช้ก็ยิ่งเพิ่ม

ส่วน PHP 7.4 นั้น [หมดการสนับสนุนจากโครงการ PHP ตั้งแต่วันที่ 28 พฤศจิกายน 2022](https://www.php.net/eol.php) แล้ว จึงควรวางแผนย้ายไปใช้ [รุ่นที่ยังได้รับการสนับสนุน](https://www.php.net/supported-versions.php) โดยทดสอบความเข้ากันได้ของเว็บก่อน การใช้ PHP 7.4 เป็นความเสี่ยงอีกส่วนหนึ่งที่ต้องแก้ แต่ไม่ได้หมายความว่า PHP เป็นช่องทางเข้าของมัลแวร์ในเคสนี้โดยตรง

ผมยกเคสนี้มาเพราะอยากให้คนที่มีเว็บหลายเว็บเผื่อเวลาและงบสำหรับการอัปเดตไว้ด้วยครับ AI ช่วยงานได้ แต่ในเคสนี้ต้นทุนและเวลาที่ใช้ยังมากเกินกว่าทีมจะรับไหว การรู้ว่าเว็บไหนยังใช้ Core เก่า และรีบลงแพตช์ก่อนเกิดปัญหา เป็นงานที่ควรทำให้ได้อย่างสม่ำเสมอ

## เว็บยังปกติแล้วต้องรีบอัปเดตด้วยหรือ

ต้องอัปเดตครับ ข้อมูลรั่วอาจไม่ทำให้หน้าเว็บล่ม และปัญหาเรื่องสิทธิ์ผู้ใช้ก็อาจไม่แสดงอะไรผิดปกติบนหน้าแรก เราจึงควรตรวจเวอร์ชันและผลการอัปเดต ไม่รอให้เว็บมีอาการก่อน

Firewall, WAF และปลั๊กอินความปลอดภัยช่วยลดความเสี่ยงบางส่วนได้ แต่ความครอบคลุมขึ้นกับกฎและบริบทของแต่ละระบบ การมีเครื่องมือเหล่านี้ไม่ได้ยืนยันว่าช่องโหว่ใน Core ถูกแก้แล้ว วิธีปิดปัญหาที่ต้นเหตุคือใช้ซอฟต์แวร์รุ่นที่มีแพตช์

เมื่อรายละเอียดปัญหาและแพตช์ออกมา ผู้โจมตีก็ศึกษาได้เช่นกันว่ารุ่นเก่าผิดพลาดตรงไหน ผมจึงแนะนำให้ลงแพตช์โดยเร็ว ไม่รอจนมีข่าวว่าเว็บอื่นโดนก่อนแล้วค่อยเริ่มสำรองข้อมูล

## ก่อนกดอัปเดต เตรียมอะไรบ้าง

ใครดูแลเว็บธุรกิจ ผมแนะนำให้เริ่มสำรองและนัดเวลาอัปเดตวันนี้ครับ ถ้ามีเว็บทดสอบให้ลองก่อน แต่ควรกำหนดด้วยว่าจะลงเว็บจริงเมื่อไร จะได้ไม่เลื่อนออกไปเรื่อย ๆ ขั้นตอนหลักดูได้จาก [คู่มือ Updating WordPress](https://wordpress.org/documentation/article/updating-wordpress/) ส่วนรายการด้านล่างเป็นสิ่งที่ผมแนะนำให้เช็กประกอบ

### 1. ตรวจเวอร์ชันและสำรองให้กู้คืนได้

เปิด **Dashboard → Updates (แผงควบคุม → อัปเดต)** เพื่อตรวจรุ่นที่ติดตั้งและรุ่นที่พร้อมอัปเดต สำรองทั้งฐานข้อมูลและไฟล์ รวมถึง `wp-content`, `wp-config.php` และการตั้งค่าเซิร์ฟเวอร์ที่จำเป็น ตรวจว่าไฟล์สำรองมีอยู่จริงและมีวิธีกู้คืนที่ใช้งานได้

เว็บร้านค้าหรือสมาชิกควรระวังข้อมูลใหม่ระหว่างสำรองกับอัปเดต โดยกำหนดช่วงดำเนินการและแนวทางรักษารายการสั่งซื้อให้ชัดเจน หากมี staging ให้ทดสอบขั้นตอนสำคัญอย่างรวดเร็วก่อนลงเว็บจริง

### 2. ลงแพตช์จากช่องทางทางการ

จากหน้า **Dashboard → Updates** กด **Update Now (อัปเดตตอนนี้)** และรอจนระบบแจ้งว่าสำเร็จ ใช้ตัวอัปเดตในหลังบ้านหรือแพ็กเกจจาก WordPress.org เท่านั้น หากโฮสติ้งเป็นผู้จัดการ Core ให้ติดต่อผู้ให้บริการเพื่อดำเนินการทันที

### 3. ตรวจเว็บหลังอัปเดต

- ยืนยันว่า Core เป็น 7.1.3 หรือรุ่นเสถียรใหม่กว่าที่ตั้งใจติดตั้ง
- เปิดหน้าแรก บทความ และหลังบ้าน ทดลองล็อกอินและบันทึกเนื้อหา
- ทดสอบฟอร์มติดต่อ การส่งอีเมล และฟีเจอร์สำคัญของเว็บ
- สำหรับร้านค้า ตรวจตะกร้า เช็กเอาต์ และการชำระเงินด้วยโหมดทดสอบที่เหมาะสม
- ล้างแคชตามระบบที่ใช้ และตรวจ error log หลังอัปเดต
- ตรวจอัปเดตปลั๊กอินและธีมด้วย เพราะการแก้ Core ไม่ครอบคลุมช่องโหว่ของส่วนเสริม
- ตรวจรุ่น PHP กับโฮสติ้งด้วย หากยังใช้ 7.4 ให้นัดทดสอบและย้ายไปรุ่นที่ยังได้รับการสนับสนุน

หากเกิดปัญหา ให้ใช้ staging, log และผู้ให้บริการโฮสติ้งช่วยหาสาเหตุ หากจำเป็นต้องกู้คืนรุ่นเดิม ให้ถือเป็นมาตรการชั่วคราวและเร่งแก้ความเข้ากันได้เพื่อลงแพตช์ใหม่ ไม่ปล่อยเว็บไว้บนรุ่นที่มีช่องโหว่โดยไม่มีแผนต่อ

## เปิดอัปเดตอัตโนมัติแล้ว ยังต้องตรวจไหม?

**ยังต้องตรวจครับ** WordPress รองรับการอัปเดตเบื้องหลังสำหรับเว็บที่เข้าเงื่อนไข แต่การตั้งค่า โฮสติ้ง หรือปัญหาระหว่างอัปเดตอาจทำให้แต่ละเว็บได้รับแพตช์ไม่พร้อมกัน ดูรายละเอียดได้ใน [คู่มือการอัปเกรดและตั้งค่าอัปเดตอัตโนมัติ](https://developer.wordpress.org/advanced-administration/upgrade/upgrading/)

ตรวจเวอร์ชันจริงในหลังบ้าน อ่านอีเมลแจ้งผล และติดตามกรณีอัปเดตล้มเหลว เว็บที่มีทีมดูแลควรกำหนดผู้รับผิดชอบและเวลาตรวจแพตช์ให้ชัด พร้อมระบบสำรองข้อมูลและการตรวจหน้าเว็บหลังอัปเดต

## คำถามที่เจ้าของเว็บมักสงสัย

### ใช้ WordPress รุ่นเก่า ได้แพตช์ย้อนหลังแล้วพอไหม?

ประกาศ 7.1.3 ระบุว่ากำลังนำการแก้ความปลอดภัยที่จำเป็นกลับไปยังสาขาที่เข้าเกณฑ์ ตั้งแต่ 4.7 ขึ้นมา และจะทยอยออกเมื่อพร้อม แต่ย้ำว่า **เฉพาะรุ่นล่าสุดเท่านั้นที่ได้รับการสนับสนุนอย่างต่อเนื่อง** จึงไม่ควรถือว่าทุกรุ่นเก่าปลอดภัยแล้วเพียงเพราะมี backport ดู [รายละเอียด Backports ในประกาศทางการ](https://wordpress.org/news/2026/10/wordpress-7-1-3-maintenance-and-security-release/)

หากยังย้ายรุ่นหลักไม่ได้ ให้ผู้ดูแลตรวจรุ่นแพตช์ของสาขาที่ใช้อยู่และติดตั้งรุ่นที่แก้ปัญหาแล้ว พร้อมวางแผนย้ายไปยังรุ่นที่ได้รับการสนับสนุน

### ปิดคอมเมนต์แล้ว ข้ามอัปเดตได้ไหม?

ไม่ควรครับ ปัญหาที่แก้ไม่ได้มีแค่คอมเมนต์ แต่ครอบคลุมการส่งออกข้อมูล สิทธิ์ผู้ใช้ การประมวลผล URL และส่วนอื่นด้วย การปิดฟีเจอร์เดียวจึงไม่ยืนยันว่าครอบคลุมทุกประเด็น

### อัปเดตแล้ว มัลแวร์ที่เคยติดจะหายไหม?

การลงแพตช์แก้ช่องโหว่ไม่ได้รับประกันว่าจะลบไฟล์อันตรายหรือบัญชีที่ผู้โจมตีสร้างไว้ก่อนหน้า หากพบผู้ดูแลแปลกปลอม ไฟล์ผิดปกติ หรือการเปลี่ยนเส้นทางที่ไม่ได้ตั้งใจ ต้องตรวจเหตุการณ์และทำความสะอาดระบบเพิ่มเติม อ่านตัวอย่างได้ใน [กรณีศึกษามัลแวร์ WordPress และจุดซ่อนตัวในระบบ](/th/blog/wordpress-malware-database-mu-plugins-case-study/)

## อย่าปล่อยแจ้งเตือนอัปเดตค้างไว้

หากยังไม่ได้อัปเดต ลองเปิดหลังบ้านตรวจรุ่นที่ใช้อยู่วันนี้ครับ สำรองข้อมูล ลงแพตช์ แล้วทดสอบว่าเว็บยังทำงานครบ หากมีหลายเว็บ ให้จดรายการว่าเว็บไหนอัปเดตแล้ว เว็บไหนติดปัญหา และใครเป็นคนตามต่อ อย่าอาศัยแค่ความจำหรือคิดว่าระบบอัตโนมัติคงจัดการให้หมดแล้ว

สำหรับแนวทางดูแลระบบต่อเนื่อง อ่านเพิ่มได้ที่ [ความปลอดภัย WordPress และการเสริมความแข็งแกร่งของระบบ](/th/blog/wordpress-security/)
