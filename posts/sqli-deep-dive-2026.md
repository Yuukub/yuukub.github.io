# SQL Injection จุดอ่อนคลาสสิกที่ยังคงสร้างหายนะให้เว็บทั่วโลก

ถ้าคุณเป็นคนทำเว็บหรือเขียนโค้ดที่ต้องยุ่งกับฐานข้อมูล คุณน่าจะคุ้นหูคำว่าระดับตำนานอย่าง SQL Injection กันมาบ้าง หลายคนอาจจะคิดว่ามันเป็นเรื่องเก่าคร่ำครึตั้งแต่วัยรุ่น Y2K แต่เชื่อไหมครับว่าในปีนี้ มันยังเป็นหนึ่งในช่องโหว่ระดับท็อปฮิตที่ทำเว็บใหญ่ๆ หน้าหงายและข้อมูลหลุดไหลกันหลักล้านบัญชี

บทความนี้เราจะมาชำแหละให้ดูว่าแฮกเกอร์ใช้ช่องทางไหนมุดเข้ามาส่องข้อมูลเราฟรีๆ แถมรูดเอาทุกอย่างไปจนเกลี้ยงเซิร์ฟเวอร์ และที่สำคัญเราจะปิดตายประตูบานนี้ได้แบบไหนบ้างแบบลงลึกถึงระดับโครงสร้าง

## กลไกความผิดพลาดระดับโครงสร้าง ทำไมแฮกเกอร์ถึงสั่งงานเซิร์ฟเวอร์เราได้

ปัญหานี้ไม่ได้เกิดจากฐานข้อมูลทำงานกากหรือเซิร์ฟเวอร์รุ่นเก่า แต่มันเกิดจากช่องโหว่ระดับสถาปัตยกรรมของภาษาคอมพิวเตอร์ที่ระบบแยกไม่ออกระหว่าง **"คำสั่ง" (Command)** และ **"ข้อมูล" (Data)**

ลองนึกภาพว่าคุณมีกล่องค้นหาสินค้าบนเว็บ เวลามีคนพิมพ์คำว่า `shoes` โค้ดหลังบ้านที่หลายคนเคยเขียนสมัยฝึกงานหน้าตาจะประมาณนี้

```php
$search = $_POST['item'];
$query = "SELECT * FROM products WHERE name = '$search'";
$db->query($query);
```

ระบบรับค่าไปต่อ String ตรงๆ ทำให้คำสั่งสมบูรณ์แบบ ได้สินค้ากลุ่มรองเท้าออกมาตามที่คาดหวัง

แต่ความบรรลัยจะเกิดทันทีถ้าช่องค้นหานั้นถูกเติมด้วยของแปลกๆ เช่น `' OR '1'='1` 
เมื่อนำไปต่อ String สิ่งที่ฐานข้อมูลมองเห็นจะเปลี่ยนไปเป็นหน้าตาแบบนี้ทันที

```sql
SELECT * FROM products WHERE name = '' OR '1'='1'
```

จุดนี้คือการล้วงตับระบบอย่างแท้จริง เพราะตรรกะ `1=1` มันเป็นจริงเสมอ ส่งผลให้เงื่อนไขการค้นหาพังทลาย ฐานข้อมูลจะปล่อยข้อมูลทุกชิ้นในตารางนั้นออกมาโชว์หน้าเว็บแบบไม่มีกั๊ก นี่คือหลักการทำงานแบบ 101 ของการทำ Injection ครับ

## ชำแหละ 4 ท่าไม้ตายที่แฮกเกอร์ใช้ดูดข้อมูล

ในโลกความเป็นจริง แฮกเกอร์มืออาชีพมักจะไม่ทำแค่นั่งเดาพาสเวิร์ดทีละตัว แต่พวกเขาจะใช้เทคนิคที่ลุ่มลึกกว่ามาก เจาะเอาโครงสร้างของฐานข้อมูลออกมาทั้งหมด มาดูกันว่ามีแบบไหนบ้าง

### In-Band SQLi (เจาะซึ่งๆ หน้า)
ทางสายตรงและได้ผลเร็วที่สุด เพราะผลลัพธ์มันจะโชว์ออกมาบนหน้าเว็บให้เห็นกันจะๆ

*   **Error-Based** แฮกเกอร์จะจงใจส่งคำสั่งผิดๆ หรือโยนค่าที่ทำให้ฐานข้อมูลประมวลผลไม่ได้ เพื่อบังคับให้เซิร์ฟเวอร์แสดงข้อความ Error Log ออกมาที่หน้าเว็บ ซึ่งข้อความแจ้งเตือนเหล่านี้มักจะคายชื่อตาราง ชื่อคอลัมน์ หรือกระทั่งเวอร์ชันของ Database ออกมาให้เห็น
*   **Union-Based** เทคนิคยอดฮิตที่ใช้เช็คบิลฐานข้อมูลอย่างรวดเร็ว ด้วยการแทรกคำสั่ง `UNION SELECT` ตามหลังคำสั่งปกติ เพื่อดึงเอาข้อมูลจาก "ตารางอื่น" เช่น ตารางเก็บรายชื่อลูกค้ารหัสผ่าน เอามาแปะรวมกับเป้าหมายเดิมที่หน้าเว็บกำลังแสดงผลอยู่

### Inferential SQLi (Blind Attack การโจมตีในความมืด)
เมื่อเว็บในปัจจุบันฉลาดพอที่จะปิดการแสดงผล Error ทิ้งหมด แฮกเกอร์จะเปลี่ยนมาใช้การ **"ถามคำถาม"** กับระบบแทน คล้ายๆ การเล่นเกมทายใจ

*   **Boolean-Based (ตอบแค่ใช่หรือไม่)** เป็นการยิงเงื่อนไขเข้าไปเช็ค เช่น "ตัวอักษรแรกของรหัสผ่านแอดมินคือตัว A ใช่หรือไม่?" ถ้าเว็บโหลดเนื้อหาปกติแปลว่าใช่ แต่ถ้าเว็บหน้าขาวหรือขึ้นข้อมูลไม่พบแปลว่าไม่ใช่ แค่นี้แฮกเกอร์ก็ใช้เครื่องมือสุ่มอักษรไปเรื่อยๆ จนประกอบร่างเป็นรหัสผ่านได้
*   **Time-Based (จับเวลาตอบสนอง)** หากการตอบสนองหน้าเว็บไม่ต่างกันเลย แฮกเกอร์จะใช้คำสั่งหน่วงเวลาอย่าง `SLEEP()` หรือ `WAITFOR DELAY` เช่น "ถ้ารหัสผ่านตัวแรกคือ A ให้เซิร์ฟเวอร์หยุดทำงานไป 5 วินาที" จากนั้นก็นั่งจับเวลาเอา ถ้าเว็บโหลดช้าผิดปกติก็แปลว่าเดาถูก เทคนิคนี้แม้จะช้าแต่มันเจาะทะลุกำแพงได้แทบทุกประเภท

### Out-of-Band SQLi (ส่งข้อมูลออกทางหลังบ้าน)
ท่าไม้ตายก้นหีบที่ใช้เมื่อเซิร์ฟเวอร์ตั้งค่าปิดกั้นแน่นหนามากจนไม่สบช่องส่งข้อมูลคืนมาที่หน้าเว็บ แฮกเกอร์จะสั่งให้เซิร์ฟเวอร์เป้าหมายสร้าง Request ใหม่ตัวนึง (เช่น HTTP หรือ DNS Request) วิ่งกระดอนไปหาเซิร์ฟเวอร์ของแฮกเกอร์เอง พร้อมแนบข้อมูลความลับแปะติดไปด้วย วิธีนี้มักรอดหูตาของระบบป้องกันไปได้บ่อยครั้ง

### Second-Order SQLi (ตีระเบิดเวลาทิ้งไว้)
หลายระบบสร้างระบบป้องกันการกรอกข้อมูลหน้า Login ไว้ดีมาก แต่ดันไปตายเอาตอนนำเอาข้อมูลมาใช้งานในภายหลัง สมมติผู้เข้าร่วมกรอกชื่อตัวเองว่า `admin'--` ตอนสมัครสมาชิกระบบกรองไว้ระดับนึงเลยบันทึกเข้าระบบได้ปลอดภัย แต่พอแอดมินเข้าไปดูหน้า Profile ระบบหลังบ้านดันเอาชื่อนั้นมาดึงค่าจากตารางแบบต่อ String ตรงๆ ทำให้คำสั่ง `--` ไป Comment โค้ดส่วนที่เหลือทิ้งหมด เกิดเป็นหายนะลูกโซ่ในเวลาต่อมา

## เทคนิคหลบเลี่ยง WAF เมื่อระบบป้องกันโดนต้มเปื่อย

คุณอาจจะคิดว่าเว็บมี Web Application Firewall (WAF) คอยช่วยดักจับก็รอดแล้ว แต่แฮกเกอร์สายเจาะระบบมีสารพัดวิธีในการพรางตัวเพื่อตบตาระบบกรองคำ (Blacklist)

*   **เปลี่ยนเว้นวรรคให้เป็นช่องโหว่** ถ้าระบบบล็อกการใช้ช่องว่าง (Space) แฮกเกอร์จะใช้คอมเมนต์มาคั่นแทน เช่น `SELECT/**/password/**/FROM/**/users` ทำให้ตัวสแกนมองไม่เห็นคำสั่งเป็นก้อนเดียวกัน
*   **ผสมตัวพิมพ์เล็กพิมพ์ใหญ่** ระบบกรองที่เขียนมาไม่ลึกพออาจหาเจอแค่ `SELECT` แฮกเกอร์เลยโยน `SeLeCt` หรือ `uNiOn` เพื่อให้ไฟร์วอลล์ตรวจจับไม่เจอ แต่ฐานข้อมูลยังคงทำงานได้ตามปกติ
*   **เข้ารหัสซ้อนทับรูปแบบต่างๆ** การใช้ฟังก์ชัน URL Encoding (`%20`), Hex Encoding, หรือกระทั่ง Unicode หลอกหน้าบ้านให้ปล่อยผ่านไปอย่างหน้าตาเฉย ก่อนที่มันจะไปสลายร่างเป็นโค้ดดั้งเดิมอันตรายตอนถึงฐานข้อมูลพอดี

## วิธีปิดรอยรั่วและป้องกันไม่ให้เกิดซ้ำ

การดักจับตัวอักษรต้องห้ามมันไม่เวิร์คอีกต่อไปแล้ว เพราะแฮกเกอร์สามารถหาหลุมหลบภัยได้เสมอ วิธีรักษารากขุดถอนโคนคือการวางโครงสร้างการเขียนโค้ดใหม่ทั้งหมด

### เขียนโค้ดกระบวนทัพใหม่ด้วย Prepared Statements
กฎเหล็กข้อบังคับขั้นสุดยอดของการเขียนโปรแกรมติดเว็บคือต้องเปลี่ยนวิธีเชื่อมต่อฐานข้อมูลมาใช้ Parameterized Queries เสมอ ไม่ว่าคุณจะใช้ภาษา PHP Database คู่ใจ หรือ Node.js ตัวเก่ง

ตัวอย่างการเขียนด้วย PDO ของ PHP สมัยใหม่
```php
$stmt = $pdo->prepare('SELECT * FROM accounts WHERE username = :user AND password = :pass');
$stmt->execute(['user' => $username, 'pass' => $password]);
$account = $stmt->fetch();
```
สิ่งที่น่าทึ่งคือฐานข้อมูลและการเตรียมคำสั่งจะแยก **"โครงสร้างคำสั่ง"** และ **"กล่องข้อมูล"** ออกจากกันตั้งแต่แรก ต่อให้แฮกเกอร์จะส่งขีปนาวุธโค้ดกี่หมื่นบรรทัดมาในช่องกรอกพาสเวิร์ด ฐานข้อมูลก็จะปฏิบัติกับมันเป็นเพียงแค่ "String ตัวหนังสือที่ยาวแปลกๆ" เท่านั้น ไม่มีการยึดเอาไปแปลผลเป็นคำสั่งเสริมเด็ดขาด

### ข้อยกเว้นของ Prepared Statements (ต้องใช้ระบบ Whitelist)
จุดตีบตันของ Prepared Statements คือมันใช้ครอบชื่อ "ตาราง" หรือ "คอลัมน์" ไม่ได้ (ฝืนใช้ในเงื่อนไขอย่าง `ORDER BY` ตรงๆ ไม่ได้) กรณีแบบนี้ผู้พัฒนาห้ามไปยืมข้อมูลจากผู้ใช้มาต่อตรงๆ เด็ดขาด ต้องเขียนโค้ดตรวจสอบผ่าน Whitelist ตามที่เราเป็นคนกำหนดอนุญาตเองเท่านั้น

```php
$allowed_sort = ['name', 'date', 'price'];
$sort_by = in_array($_GET['sort'], $allowed_sort) ? $_GET['sort'] : 'date';
// คราวนี้ถึงเอา $sort_by ไปต่อ String ได้อย่างสบายใจไร้กังวล
```

### ทำงานร่วมกับ ORM ยุคใหม่
Developer สาย Modern มักใช้ Framework ที่มีระบบ ORM ผูกติดมาให้แล้ว เช่น Prisma ของ Node.js, Entity Framework ของ C#, หรือ Eloquent ของ Laravel ระบบเหล่านี้ฉลาดพอที่จะกรองช่องโหว่นี้ด้วยการทำ Prepared Statement ให้เบื้องหลังตั้งแต่ชั้นรากฐานโดยที่เราไม่ต้องเหนื่อยเขียนเตรียมข้อมูลเองทุกรอบ

### จำกัดอำนาจ Database User (Principle of Least Privilege)
แอดมินหลายคนชอบมักง่ายเอา User ระดับ `root` เพเทียบ่ามาฝังในโค้ดเชื่อมกับเว็บแอปพลิเคชันทุกหน้า ซึ่งมันสุ่มเสี่ยงถึงชีวิตมาก หลักการที่ถูกต้องคือควรหั่นสิทธิ์ให้เล็กที่สุด หน้าเว็บสำหรับโชว์แคตตาล็อกสินค้าก็ควรมีสิทธิ์บัญชีการเข้าถึงแค่ `SELECT` หน้าเว็บเปิดตั๋วสมัครสมาชิกถึงจะค่อยให้บัญชีที่มีสิทธิ์ `INSERT` วิธีนี้ต่อให้หลุดไปได้จริงๆ โค้ดของแฮกเกอร์ก็ไม่มีวันมาระเบิดตารางด้วย `DROP TABLE` เราทิ้งได้

---

SQL Injection ไม่ใช่มนตร์ดำที่ลี้ลับยากเกินจะต่อกร แต่มันเกิดจากความประมาทของการปล่อยให้ข้อมูลภายนอกหลุดเข้าไปปะปนรบกวนโครงสร้างคำสั่งภายใน หากเราวางระเบียบการจัดเก็บและแยกแยะประเภทข้อมูลให้รอบคอบตั้งแต่ตอนเขียนโค้ด กำแพงป้องกันของเราก็จะแข็งแรงจนแฮกเกอร์ต้องยอมถอยไปเองครับ
